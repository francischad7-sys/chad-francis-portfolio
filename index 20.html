Electric Dirt Bike Build

A ground-up electric dirt bike build using components sourced directly from international suppliers. Each component was specified against performance targets of 55 mph and 30 miles of range; the first full test reached 61 mph.

Top speed
61 mph
Voltage
72 V
Motor
8000 W
  • Selected a 3.5T hub-motor winding as a deliberate compromise between the top speed of a 3T winding and the torque of a 5T.
  • Validated the electrical system through voltmeter checks and powered drivetrain tests before final assembly.
  • Diagnosed a blown fuse caused by excess current from the 150 A controller and resolved it with a 100 A unit, trading top speed (53 mph) for reliability.
  • Engineered a custom wiring harness to resolve a controller-to-throttle incompatibility, learning to solder in the process.

My role: Sole designer and builder, responsible for component selection, vendor communication, assembly, testing, and iterative repair.

What I learned4 takeaways
  1. Peak numbers aren't the goal.The 150 A controller hit 61 mph but blew a fuse. Dropping to 100 A cost 8 mph and made the bike dependable, and that trade was the right one.
  2. Range depends on how you use the energy.Running the pack hard gave about 10 miles instead of 30 and wore the cells down early. Discharge rate matters as much as capacity.
  3. Design for vibration from day one.An enclosure with no damping let rough terrain damage the electronics inside. I went back and insulated the battery, and an unbalanced tire taught me the same lesson.
  4. Integration is where builds break.Parts from different vendors don't always talk to each other. A throttle-to-controller mismatch is how I learned to solder and build a custom harness, and why I now test each subsystem before final assembly.

An autonomous robot that tours a table-sized model of campus: four stops, in order, no human input, under three minutes. It knows where it is from overhead cameras, sees walls with three ultrasonic sensors, and lives in a 3D-printed body we designed in SolidWorks.

01Thought processHow the design and tuning decisions evolved

The brief was simple to say and hard to do: drive to four stops in order, touch nothing, finish under three minutes. We treated it as three problems that had to agree with each other: where the robot is, what is around it, and how it moves.

How the thinking evolved

  1. 01 · Frame itKnow where you are, see what's around you, then move

    Position comes from the arena's overhead cameras reading an ArUco marker on the robot and publishing x, y and heading over MQTT. Three ultrasonic sensors cover front, left and right. The WeMos D1 R2 was chosen for its built-in Wi-Fi.

  2. 02 · First structureTwo tiers on pillars, clipped to the chassis

    The first concept stacked two plates on four pillars and clamped the base on with printed clips. The clips didn't hold the way we expected, so the base moved to nuts and bolts, and the pillars gave way to walls the top tier slides onto, which made the whole body stiffer and easier to assemble.

  3. 03 · Design around the partsEvery component gets a home

    The top tier became angular to match the sensor angles, with a cut-out for wiring. As the build grew, we added a slot for the power switch, branches that the motor driver snaps onto, a window for the OLED and holes for the wire lug, until nothing was loose.

  4. 04 · Make the sensors seeFour versions of the sensor hanger

    The detail that mattered most was height. Earlier hangers held the sensors above the arena's building walls, so the robot couldn't see what it was about to hit. The final hanger drops the sensor closer to the ground.

    V1

    Slide-in holder, built for the pillar design

    V2

    Hook branches to hang from the top-tier pegs

    V3

    Longer branches so three sensors fit side by side; rear-loaded sensor

    V4 · final

    Front extended downward so sensors sit below the wall tops

  5. 05 · Tune the behaviorSlow it down, then earn the speed back

    Early runs hit walls because the robot was moving too fast to stop in time. We slowed it right down and widened the obstacle margin, which fixed the collisions but made stop 4, tucked into a tight nook, unreachable. We then narrowed the wall tolerance step by step until it could turn in, and only after that raised motor speed back up for a competitive time.

  6. 06 · Debug the boring stuffMost "software" bugs were wiring

    Spinning in circles and turning the wrong way usually traced back to swapped motor wires or left/right speeds assigned to the wrong side. The sensors and OLED also misbehaved when Serial was used or the TX/RX pins were left connected during upload.

What I'd do differently

Plan the routing

The robot sometimes hesitated between paths or didn't take the shortest one. Smarter path selection would cut the time further.

Solder early

Jumper wires kept unplugging during testing. Trimming and soldering them saved space and stopped intermittent failures.

Measure before printing

Some reprints were unavoidable, like adding the power switch late, but others could have been avoided by measuring every part up front.

02Robot sequence treeThe decision order the robot runs every loop

Every loop the robot reads its position and all three sensors, computes the distance and heading error to the current stop, then walks down this list from the top. The first check that's true decides the move, and the loop starts again. Order is the whole design: reaching a stop beats everything, and safety beats steering.

loop() · read MQTT x, y, θ · read front / left / right · compute dist, err
  1. Arrive
  2. 1dist < reach radius?
    Stop for 2 s, advance to the next stop, clear all timers. Radius is 150, or 115 for the tight stop 4.
  3. Committed actions (timers)
  4. 2just started and front clear?
    Startup glide: drive forward at adaptive speed.
  5. 3reverse timer running?
    Reverse until it expires.
  6. 4turn timer running?
    Turn toward the chosen side (left or right).
  7. 5re-acquire window open?
    Still blocked → re-avoid. Else err > 10° → swerve left, err < −10° → swerve right, else drive.
  8. Obstacles
  9. 6front < 11 cm?
    Emergency: reverse 85 ms, turn 115 ms toward the open side, then re-acquire.
  10. 7front < 27 cm (31 at stop 4)?
    Turn away for 90 ms toward the side with more room, then re-acquire.
  11. 8left or right < 8 cm (6 at stop 4)?
    Turn away from that wall for 75 ms, then re-acquire.
  12. Steering to the target
  13. 9steered < 125 ms ago?
    Soft swerve toward the target, or drive straight if aligned.
  14. 10|err| > 28° (38° at stop 4)?
    Swerve hard toward the target. Curving instead of spinning in place.
  15. 11|err| > 10°?
    Swerve toward the target.
  16. 12otherwise
    Drive forward at adaptive speed.
θ = heading from the overhead cameraerr = bearing to target − θ, wrapped to ±180°

03CodeKey functions explained, plus the full firmware

Written in C++ in the Arduino IDE for the WeMos D1 R2. Our software lead wrote most of the firmware; I helped test and tune it on the course. The highlights first, then the full files.

Key pieces

Heading error, wrapped so the robot always turns the short way.

float angleErr(float dx, float dy) {
  float a = atan2(dy, dx) * 180.0 / PI - z_ang_robot;
  while (a > 180) a -= 360;
  while (a < -180) a += 360;
  return a;
}

Cleaning sensor noise. Ultrasonics sometimes return 0 or huge values, so those become "nothing close."

int clean(int d) {
  if (d <= 0 || d > 400) return 999;
  return d;
}

Choosing a side and committing to it, so the robot doesn't flip back and forth.

void chooseAvoidDir(int l, int r) {
  if (l > r + 5) avoidDir = 1;        // more room on the left
  else if (r > l + 5) avoidDir = -1;  // more room on the right
  else avoidDir = 1;                  // tie: default left
}

#include <Wire.h>
#include <Servo.h>
#include <Ultrasonic.h>
#include "MQTT.h"

Servo motorLeft;
Servo motorRight;

Ultrasonic ultrasonicFront(D5, D8);
Ultrasonic ultrasonicRight(D4, D7);
Ultrasonic ultrasonicLeft(TX, D0);

// the four tour stops, in arena coordinates
int targets[][2] = {
  {750, 730},
  {1650, 150},
  {2220, 650},
  {150, 150}
};

const int numTargets = 4;
int targetIndex = 0;

// -------- MOTOR VALUES --------
const int stopMotor = 90;

// fast but smooth
void forwardFast()  { motorLeft.write(123); motorRight.write(123); }
void forward()      { motorLeft.write(119); motorRight.write(119); }
void forwardSlow()  { motorLeft.write(114); motorRight.write(114); }
void forwardCreep() { motorLeft.write(109); motorRight.write(109); }

// smoother steering
void swerve_left_soft()  { motorLeft.write(121); motorRight.write(115); }
void swerve_right_soft() { motorLeft.write(115); motorRight.write(121); }

void swerve_left()  { motorLeft.write(122); motorRight.write(113); }
void swerve_right() { motorLeft.write(113); motorRight.write(122); }

// short turns only when truly needed
void turn_left()  { motorLeft.write(122); motorRight.write(97); }
void turn_right() { motorLeft.write(97);  motorRight.write(122); }

void reverse_drive() { motorLeft.write(70); motorRight.write(70); }
void stopDrive()     { motorLeft.write(stopMotor); motorRight.write(stopMotor); }

// -------- thresholds --------
const int frontEmergency   = 11;
const int frontBlockNormal = 27;
const int frontBlockFourth = 31;

const int sideBlockNormal = 8;
const int sideBlockFourth = 6;

const int targetReachDistNormal = 150;
const int targetReachDistFourth = 115;

// angle thresholds
const int bigAngleNormal = 28;
const int bigAngleFourth = 38;
const int smallAngle     = 10;

// timing
const unsigned long targetActionDelay = 125;
unsigned long lastTargetActionTime = 0;

unsigned long reverseUntil   = 0;
unsigned long turnUntil      = 0;
unsigned long startupUntil   = 0;
unsigned long reacquireUntil = 0;

int avoidDir = 1; // 1 = left, -1 = right

int clean(int d) {
  if (d <= 0 || d > 400) return 999;
  return d;
}

float angleErr(float dx, float dy) {
  float a = atan2(dy, dx) * 180.0 / PI - z_ang_robot;
  while (a > 180) a -= 360;
  while (a < -180) a += 360;
  return a;
}

float distToTarget(float dx, float dy) {
  return sqrt(dx * dx + dy * dy);
}

void nextTarget() {
  targetIndex = (targetIndex + 1) % numTargets;
}

void chooseAvoidDir(int l, int r) {
  if (l > r + 5) avoidDir = 1;
  else if (r > l + 5) avoidDir = -1;
  else avoidDir = 1;
}

void driveForwardAdaptive(bool goingToFourth, float dist, int f) {
  if (goingToFourth) {
    if (dist < 145)                 forwardCreep();
    else if (dist < 255 || f < 42)  forwardSlow();
    else if (f > 105)               forwardFast();
    else                            forward();
  } else {
    if (dist < 220)      forwardSlow();
    else if (f < 36)     forwardSlow();
    else if (f > 100)    forwardFast();
    else                 forward();
  }
}

void startReacquire(unsigned long now) {
  reacquireUntil = now + 220; // brief target re-lock after avoidance
}

void setup() {
  motorLeft.attach(D6);
  motorRight.attach(D3);
  stopDrive();
  wifi_mqtt_init();
  startupUntil = millis() + 450;
}

void loop() {
  mqtt_rebound();
  client.loop();

  int f = clean(ultrasonicFront.read(CM));
  int l = clean(ultrasonicLeft.read(CM));
  int r = clean(ultrasonicRight.read(CM));

  float dx   = targets[targetIndex][0] - x_robot;
  float dy   = targets[targetIndex][1] - y_robot;
  float dist = distToTarget(dx, dy);
  float err  = angleErr(dx, dy);

  bool goingToFourth  = (targetIndex == 3);
  int sideBlock       = goingToFourth ? sideBlockFourth : sideBlockNormal;
  int frontBlock      = goingToFourth ? frontBlockFourth : frontBlockNormal;
  int targetReachDist = goingToFourth ? targetReachDistFourth : targetReachDistNormal;
  int bigAngle        = goingToFourth ? bigAngleFourth : bigAngleNormal;
  unsigned long now   = millis();

  // -------- target reached --------
  if (dist < targetReachDist) {
    stopDrive();
    delay(2000);
    nextTarget();
    reverseUntil = 0;
    turnUntil = 0;
    reacquireUntil = 0;
    startupUntil = millis() + 280;
    return;
  }

  // -------- startup glide --------
  if (now < startupUntil && f > frontBlock + 8) {
    driveForwardAdaptive(goingToFourth, dist, f);
    return;
  }

  // -------- committed obstacle actions --------
  if (now < reverseUntil) {
    reverse_drive();
    return;
  }

  if (now < turnUntil) {
    if (avoidDir == 1) turn_left();
    else turn_right();
    return;
  }

  // -------- immediate target reacquire after avoidance --------
  // After turning away from a wall, do not keep wandering.
  // Smoothly bend back toward the target.
  if (now < reacquireUntil) {
    if (f < frontBlock - 2) {
      chooseAvoidDir(l, r);
      turnUntil = now + 80;
      reacquireUntil = 0;
      return;
    }
    if (err > smallAngle)  { swerve_left();  return; }
    if (err < -smallAngle) { swerve_right(); return; }
    driveForwardAdaptive(goingToFourth, dist, f);
    return;
  }

  // -------- obstacle avoidance --------
  if (f < frontEmergency) {
    chooseAvoidDir(l, r);
    reverseUntil = now + 85;
    turnUntil = reverseUntil + 115;
    startReacquire(turnUntil);
    return;
  }

  if (f < frontBlock) {
    chooseAvoidDir(l, r);
    turnUntil = now + 90;
    startReacquire(turnUntil);
    return;
  }

  if (l < sideBlock) {
    avoidDir = -1;
    turnUntil = now + 75;
    startReacquire(turnUntil);
    return;
  }

  if (r < sideBlock) {
    avoidDir = 1;
    turnUntil = now + 75;
    startReacquire(turnUntil);
    return;
  }

  // -------- smooth target steering --------
  if (now - lastTargetActionTime < targetActionDelay) {
    if (err > smallAngle)       swerve_left_soft();
    else if (err < -smallAngle) swerve_right_soft();
    else                        driveForwardAdaptive(goingToFourth, dist, f);
    return;
  }

  // large heading error: curve back instead of spinning in place
  if (err > bigAngle)  { swerve_left();  lastTargetActionTime = now; return; }
  if (err < -bigAngle) { swerve_right(); lastTargetActionTime = now; return; }

  if (err > smallAngle)  { swerve_left();  lastTargetActionTime = now; return; }
  if (err < -smallAngle) { swerve_right(); lastTargetActionTime = now; return; }

  driveForwardAdaptive(goingToFourth, dist, f);
  lastTargetActionTime = now;
}

Color code

Red is power, black is ground. Blue carries trigger, S1 and SCL; green carries echo, S2 and SDA. Keeping one scheme across every part made debugging much faster.

Takeaways

What I learned.

Sensing is partly a mechanical problem.

The code was fine, but the sensors were mounted above the wall tops and couldn't see them. Lowering the hanger fixed it.

Get it right slowly, then make it fast.

We fixed collisions by slowing down and widening the safety margins, then tightened them and added speed back step by step.

In a control loop, the order is the design.

Deciding what the robot checks first, like arriving, then safety, then steering, removed most of the erratic behavior.

Check the hardware before the code.

Swapped motor wires and occupied TX/RX pins looked like software bugs. Soldered connections stopped the intermittent failures.

Split by strengths, solve together.

We divided the CAD, code and wiring by strength, but the hardest problems got fixed when all three of us worked on them together.

Result

All four stops in 1:25.

In the final run the robot reached every stop in less than half the time limit, with a single wall bump, and earned full marks for performance.
